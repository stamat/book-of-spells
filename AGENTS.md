# Book of Spells — agent notes

A JavaScript utility library: small, dependency-free helpers in ES modules,
grouped by subject. Some run anywhere, some touch the DOM.

## Commands

```bash
script/test      # jest
script/bench     # every bench/<function>/; `--full` for the big sizes
script/build     # regenerates the docs and the type declarations
script/types     # type declarations only
```

## Layout

- `src/*.mjs` is the library, one file per subject — `dom`, `elements`,
  `parsers`, `helpers`, `regex`, `cookies`, `localstorage`, `animations`,
  `browser`, `entities`.
- `index.mjs` re-exports them; a new module is added there, and to `files` in
  `package.json` if it lives outside `src/`.
- Tests live in `src/__tests__/`.
- Benchmarks live in `bench/<function>/*.bench.mjs` — runnable node scripts,
  not shipped. Every contender's output is asserted correct before its timing
  is reported. `bench/harness.mjs` is shared; anything else a bench needs lives
  in its own directory.
- The library is dependency-free and stays that way. A bench racing
  third-party rivals declares them in its own directory's `package.json`, never
  in the root: `npm run setup` there installs them at pinned versions and
  downloads any real corpus, `npm run bench` runs that directory,
  `npm run teardown` removes both. A bench whose rivals are absent prints the
  setup line and skips, so `script/bench` on a fresh checkout still runs
  everything else.
- Benches run on generated data by default — seeded, no `Math.random`, so a
  published number can be rerun by a stranger. `--corpus <file>` swaps in real
  data for realism, and downloaded corpora are gitignored, never committed.
- A bench comparing what rivals *can answer* rather than how fast, run every
  cell in a child process — `bench/deepEqual/` is the worked example. A rival
  that neither returns nor throws cannot be caught in-process, and one such
  cell would hang the whole suite instead of being reported as a row.
- `types/` and `docs/` are **generated** — `docs/` is gitignored, `types/` ships
  in the package.

## Documentation

The docs are the JSDoc, and nothing else. `npm run docs` runs
[JSDoc](https://jsdoc.app/) over `src/` and `README.md` with the config in
[jsdoc.json](jsdoc.json), writing `docs/`, which
[pages.yml](.github/workflows/pages.yml) deploys. `npm run types` runs `tsc`
over the same comments to emit `types/`.

That makes the comment above a function load-bearing twice over: it is the
documentation site _and_ the type declaration a consumer's editor reads.

- **Every exported function has a JSDoc block** with `@param`, `@returns` and
  at least one `@example` that runs. An undocumented export is an export nobody
  can use and a `any` in someone's editor.
- **Document in the same change as the code.** Behaviour that changed and a
  comment that did not is worse than no comment.
- **Do not hand-edit `docs/` or `types/`.** They are regenerated by
  `script/build`; edit the JSDoc.
- **README.md is part of the doc build** — the subject list and the usage
  section belong there, not in a new markdown file.

## Principles

- **No dependencies.** The package ships none, and that is the point. A helper
  that needs one belongs in the project that needs it.
- **Test-driven.** The test is the spec; write it first. A failing test means
  the code is wrong — never weaken, skip, or delete a test to make it pass.
- **YAGNI.** Build only what the task needs — no speculative options or "for
  later" scaffolding.
- **Platform first.** If the language or the DOM already does it — `structuredClone`,
  `URLSearchParams`, `Object.groupBy`, `element.closest` — there is no helper.
  A helper earns its place by covering what the platform makes awkward, not by
  renaming it.
- **Root cause over symptom.** Fix where all callers route through, not the one
  path the bug report names.
- **Delete dead code.** No commented-out blocks — git remembers.

## Boundaries

- **Always:** run `script/test` before calling work done; pair every fix or
  feature with a test; keep the JSDoc current; add a changelog entry under
  `## [Unreleased]`.
- **Ask first:** changing a function's signature or return shape — this is a
  published library and someone calls it; adding a dependency; adding a new
  subject module.
- **Never:** edit `docs/` or `types/` by hand (generated); weaken, skip, or
  delete a test to make it pass; bump the version or publish — `script/publish`
  and a tag do that.

## Before adding a feature

Run this checklist before writing any code; stop at the first "no".

1. **Does the language or the DOM already do it?** Then there is no helper.
2. **Does something in `src/` already do it?** Check the neighbouring subject
   module before writing a second one.
3. **Search for prior art.** How do lodash, or the platform's own proposals,
   name and shape it? Cite what you found — a URL per fact, no guesses. Can we
   do it more simply? Does it benefit this library?
4. **Is it general?** A helper written for one project's shape of data belongs
   in that project.
5. **Still yes?** Build the smallest version that works, in the module where it
   belongs.

## Non-obvious rules

- **Jest runs in ESM mode** — `NODE_OPTIONS='--experimental-vm-modules'` is in
  the `test` script for that reason — under jsdom, and matches
  `**/__tests__/**/*.test.mjs`. A test file named `.js` is a test that never
  runs.
- **`types/` is committed and shipped**, so a signature change is not finished
  until `script/types` has been run and the result committed.
- **Browser helpers must degrade.** Several of these run at import time in a
  page; assume no DOM and no `window` until proven otherwise.
